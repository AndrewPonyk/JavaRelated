# `native/` — the OpenCV bridge

This directory builds `pip_enhance`, a small C++ shared library that implements the
`ImageEnhancer` SPI with OpenCV. **It is optional.** The application builds, tests,
and runs without it; `PassthroughEnhancer` takes over and the status bar says so.

If you are here because `mvn verify` failed, you are in the wrong directory —
nothing in this folder participates in the Maven build.

---

## 1. Why the native part is at arm's length

Everything else in this project fails politely. A corrupt JPEG becomes a
`JobOutcome.Failure`; a missing output directory becomes an `ImageIoException`. A
mistake in C++ does none of that — it is a segfault, which is not an exception but
a dead JVM, no stack trace, and a user who has no idea which of their 4 000
photographs caused it.

So the boundary is drawn to make that outcome as unlikely, and as survivable, as
possible:

| Risk | Where it is handled |
|---|---|
| Library missing | `NativeLibraryLoader` catches `Throwable`, logs `WARNING`, `isAvailable()` → `false` |
| Library present but stale | ABI version handshake (`nativeApiVersion`) refuses a mismatch at startup |
| OpenCV throws | `try/catch (cv::Exception)` in every entry point; failure becomes a `null` return |
| Bad arguments from Java | Re-validated in C++ — length, bounds, pixel cap — never trusted |
| `dnn_superres` not installed | Compiled out; `nativeSupports` reports `false`; Java passes the image through |
| Mode enum reordered | Explicit `CODE_*` wire constants, not `ordinal()` |

The one risk **not** mitigated is a genuine bug inside OpenCV or inside
`pip_enhance.cpp`. That is why the library is optional, and why a release is
expected to be usable without it.

## 2. Prerequisites

- A C++17 compiler (MSVC 2019+, GCC 9+, Clang 10+)
- CMake 3.20+
- OpenCV 4.x with `core`, `imgproc`, `photo`
- `JAVA_HOME` pointing at **the same JDK 21 that builds `pip-native`**

`dnn_superres` (from `opencv_contrib`) is optional and usually absent from
distribution packages. Without it, `SUPER_RESOLUTION` reports itself unsupported
and images pass through unchanged — which is a supported configuration, not a
degraded one.

### Installing OpenCV

```bash
# Debian / Ubuntu
sudo apt-get install libopencv-dev

# Fedora
sudo dnf install opencv-devel

# macOS
brew install opencv
```

On Windows there is no package manager doing this for you. Download the official
self-extracting archive from opencv.org, extract it to e.g. `C:\opencv`, and either
let `cmake/FindOpenCVLocal.cmake` guess or pass the path explicitly:

```
-DOpenCV_DIR=C:/opencv/build/x64/vc17/lib
```

That directory — the one containing `OpenCVConfig.cmake` — is not guessable, which
is the entire reason `FindOpenCVLocal.cmake` exists.

## 3. Building

```bash
# From the repository root. The generated JNI header must exist first:
mvn -q -pl pip-native -am compile

cmake -S native -B native/build -DCMAKE_BUILD_TYPE=Release
cmake --build native/build --config Release
cmake --install native/build
```

Or just `scripts/build-native.cmd` / `scripts/build-native.sh`, which do the same
and check `JAVA_HOME` first — its absence is the most common first failure and the
CMake error it produces (`Could NOT find JNI`) does not say so.

`cmake --install` writes the library straight into

```
pip-native/src/main/resources/native/<os>-<arch>/
```

so the next `mvn package` bundles it with no further steps. The `<os>-<arch>`
spelling is produced twice — by `CMakeLists.txt` and by
`NativeLibraryLoader.platformDirectory()` — and the two **must** agree. They are
normalised identically (`amd64`/`x64` → `x86_64`, `arm64` → `aarch64`,
`darwin` → `macos`) because `os.arch` reports different strings for the same CPU
depending on which vendor's JDK is asking.

## 4. Regenerating the JNI header

**Never edit `include/com_parallelimage_nativebridge_NativeImageEnhancer.h`.** It is
generated by `javac -h` on every `mvn compile` of `pip-native` (see the
`maven-compiler-plugin` configuration in that module's POM).

Editing it by hand is how the mangled names drift from the Java declarations, and
the symptom is an `UnsatisfiedLinkError` naming a method that visibly exists in both
files. Change the `private static native` declarations in `NativeImageEnhancer.java`,
rebuild the module, and the header follows.

## 5. The data contract

```
ByteBuffer argb, ByteBuffer out, int width, int height  →  ByteBuffer (== out), or null
```

- Both buffers are **direct** (`ByteBuffer.allocateDirect`) and **little-endian**
  (`ByteOrder.LITTLE_ENDIAN`). A non-direct buffer has no stable native address, so
  `GetDirectBufferAddress` would return `nullptr` for one — which is exactly what
  the C++ side treats it as.
- **Packed ARGB**, row-major, exactly `width * height * 4` bytes. No stride, no
  offset. `NativeImageEnhancer.compactArgb` guarantees this, and the C++ side
  checks it anyway with `GetDirectBufferCapacity` on both buffers.
- `CV_8UC4` over the same memory is B,G,R,A on a little-endian machine, which is
  what a Java `0xAARRGGBB` int looks like byte by byte. That is why no per-pixel
  shuffle is needed — and why this code assumes a little-endian JVM. There are no
  supported big-endian JDK 21 builds, so the assumption is documented rather than
  handled.
- `argb` **must not be mutated**: the engine may still be holding the source
  image. `out` is where the callee writes its result; the caller pre-sizes it to
  exactly the expected byte count before the call.
- **`null` means "not implemented"** (or an internal failure), not necessarily a
  reportable error. The Java side logs it at `DEBUG` and uses the unenhanced
  image. On success the callee returns `out` itself — never a newly allocated
  buffer, so there is nothing for the JVM to fail to free.
- A geometry change is not representable at all: `out` is pre-sized by the Java
  side to `width * height * 4` bytes before the native call, so there is no
  differently-sized result for the callee to hand back. A mode that produces a
  different size belongs in a separate, non-tileable `ImageOperation` with a
  declared output size, not in this SPI.

### `GetDirectBufferAddress`

Used instead of `GetPrimitiveArrayCritical`/`GetIntArrayElements` because a direct
buffer's memory is already off-heap and fixed in place — the JVM never moves or
collects it out from under a pointer obtained here. Unlike
`GetPrimitiveArrayCritical`, holding the pointer carries **no ban on JNI calls or
allocations**, so the GC is never paused for the duration of the native call. The
result is written directly into the caller-supplied `out` buffer with `memcpy`;
there is no equivalent of `ReleasePrimitiveArrayCritical` to call for a direct
buffer.

## 6. Thread safety

`enhance` is called concurrently by every worker in the pool. The native side is
stateless apart from the lazily-loaded super-resolution model, which is guarded by
`std::call_once` in C++ *and* serialised by a `ForkJoinPool.ManagedBlocker` in Java.

That double guard is not redundancy for its own sake — they solve different
problems. `call_once` prevents two loads; the `ManagedBlocker` tells the pool that
the waiting workers are *idle*, so it starts a compensating thread instead of
letting parallelism collapse to N−1 while a 50 MB model is read off disk.

Note carefully what is **not** wrapped in a `ManagedBlocker`: the per-image OpenCV
calls. Those are CPU-bound. Compensating for them would start extra threads to
fight over cores that are already saturated — the batch gets slower while a thread
dump makes it look like it got more parallel. `ManagedBlocker` is for threads that
are idle, which is not the same as threads that are slow.

## 7. CI and `-Xcheck:jni`

`.github/workflows/native-build.yml` is the only CI context that actually builds
`pip_enhance` and installs it where `NativeLibraryLoader` will find it — everywhere
else in CI, this module is exercised with no native library present and
`PassthroughEnhancer` quietly takes over. So it is also the only place a JNI bug
could ever be caught before a user hits it, and that workflow runs its Maven step
with

```
-Dpip.surefire.extraArgs=-Xcheck:jni
```

`-Xcheck:jni` makes the JVM validate every JNI call's arguments and return values —
wrong types, dangling local refs, a `jobject` from the wrong `JNIEnv` — and abort
with a diagnostic instead of silently corrupting the heap. It costs real throughput,
which is why `pip.surefire.extraArgs` is empty everywhere else (see `pom.xml`); this
is a correctness gate, not something to run on every `mvn test`.

What it does **not** catch is the risk this whole module is built around: a genuine
segfault inside OpenCV or `pip_enhance.cpp` itself still kills the JVM outright, with
no exception and no stack trace, `-Xcheck:jni` or not. That is Risk Register **R1**
in `docs/PROJECT-PLAN.md` — this section only documents how CI narrows the *other*
class of JNI bug (a wrong boundary call), not how it survives that one.

## 8. Debugging a load failure

```bash
# What did the loader actually try?
java -Djava.util.logging.ConsoleHandler.level=ALL ... 2>&1 | grep -i native

# Point it at a fresh build without installing anything:
java -Dpip.native.library=/abs/path/to/native/build/libpip_enhance.so ...

# What does the library depend on that is missing?
ldd  native/build/libpip_enhance.so    # Linux
otool -L native/build/libpip_enhance.dylib   # macOS
dumpbin /dependents native\build\Release\pip_enhance.dll   # Windows
```

`UnsatisfiedLinkError: ... can't find dependent libraries` on Windows almost always
means `opencv_world4xx.dll` is not on `PATH`. The OpenCV DLLs live in
`C:\opencv\build\x64\vc17\bin`, which the installer does not add for you.

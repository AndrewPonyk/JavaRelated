# Database migrations

Schema for **optional** persistence of a run's aggregates.

## Read this first: nothing here runs by default

The pipeline's default repository is
[`InMemoryAggregateRepository`](../src/main/java/com/example/pipeline/infrastructure/persistence/InMemoryAggregateRepository.java).
A database is opt-in, selected by setting `pipeline.jdbc.url`, and the JDBC
implementation behind that switch
([`JdbcAggregateRepository`](../src/main/java/com/example/pipeline/infrastructure/persistence/JdbcAggregateRepository.java))
is a **documented stub that throws on `save`**.

So the honest description of this directory is: *reviewable schema for a
feature that is designed but not implemented.* That ordering is intentional —
the shape of the data is the part worth arguing about before any code exists,
and a schema is far cheaper to change now than after a table has rows in it.

## Why there is no migration runner

No Flyway, no Liquibase, no jar. The project commits to zero runtime
dependencies (`docs/ARCHITECTURE.md` §2.6), and adding a migration framework
to serve a repository that throws would be a dependency in service of nothing.

The files follow Flyway's `V<version>__<description>.sql` convention anyway, so
dropping Flyway in later is a `pom.xml` edit and nothing else — the filenames
already carry the ordering it needs.

Until then, apply them by hand:

```bash
# PostgreSQL
psql -h localhost -U pipeline -d pipeline -v ON_ERROR_STOP=1 \
  -f migrations/V001__create_pipeline_tables.sql \
  -f migrations/V002__add_indexes.sql
```

`ON_ERROR_STOP=1` is not optional. Without it `psql` reports failures and
keeps going, leaving a half-applied schema that looks like a success.

## Files

| File | Contents |
| --- | --- |
| `V001__create_pipeline_tables.sql` | `pipeline_run`, `sensor_aggregate`, the `sensor_aggregate_report` view |
| `V002__add_indexes.sql` | Indexes, incl. the partial ones for failed/lossy runs |

Both are idempotent (`IF NOT EXISTS` throughout), so a re-run after a partial
failure needs no manual cleanup.

## The model in one paragraph

One `pipeline_run` row per completed run, holding both the settings it ran with
and the counters it produced; one `sensor_aggregate` row per sensor per run,
holding `count / min / max / sum`. The mean is **never stored** — it is derived
on read, in the `sensor_aggregate_report` view and in
`AggregateResult.average()`. A stored mean cannot be merged, and mergeability
is exactly the property that makes the fork/join aggregation legal
(`AggregateResult.merge` is a commutative monoid). Storing a mean would encode
the one number that breaks if you ever shard the aggregation.

## Two constraints worth defending

**`ck_pipeline_run_reconciles`** —
`events_produced = events_passed + events_rejected + lost_events`.

This is the pipeline's central invariant, already checked by
`PipelineOrchestrator` after every stage terminates. Enforcing it in the
database as well is not redundancy for its own sake: the check in Java protects
the report, and the check here protects *history*. If a future bug computes
`lost_events` wrongly, the insert fails and the run is reported as failed —
rather than a wrong-but-plausible row surviving in a table people later trust.

**`elapsed_millis` stored, not derived** — `finished_at - started_at` looks
like the same number and is not. Elapsed time is measured with
`System.nanoTime()` (monotonic); the timestamps come from a wall clock that can
step backwards over an NTP correction, which makes the subtraction negative.

## Dialect

Written for **PostgreSQL 14+**. Two constructs are not portable, both flagged
inline in the SQL:

* `BIGSERIAL` → `BIGINT GENERATED BY DEFAULT AS IDENTITY` (H2, standard SQL) or
  `INTEGER PRIMARY KEY AUTOINCREMENT` (SQLite).
* Partial indexes (`CREATE INDEX ... WHERE`) → supported by SQLite, **not** by
  H2. Drop the `WHERE` clause there; the test table is small enough that the
  distinction is theoretical.

`TIMESTAMPTZ` is `TIMESTAMP WITH TIME ZONE` on both. Never plain `TIMESTAMP`:
a run's start time without an offset is ambiguous the moment two machines in
different zones write to the same table.

## Finishing the implementation

The Phase 3 TODO in `docs/PROJECT-PLAN.md`, in the order it has to happen:

1. Add a JDBC driver dependency and `requires java.sql`, then extend the
   documented `jlink` module list in `docs/TECH-NOTES.md` §3.3 — it currently
   reads `java.base, java.logging, jdk.httpserver`, and referencing
   `java.sql` silently invalidates it. (This is why the stub imports no
   `java.sql` type today.)
2. Accept a `DataSource`, or open one connection per `save`. **Never** a shared
   `Connection` — it is not thread-safe, and `AggregateRepository` is
   documented as thread-safe.
3. Insert the `pipeline_run` row, then batch-insert the `sensor_aggregate` rows
   **inside one transaction**, so a partial write is never visible. The unique
   constraint on `(run_id, sensor_id)` is what makes a retry safe.
4. `PreparedStatement` throughout. The sensor id is data; it never reaches a
   statement by string concatenation.
5. Retention. Nothing prunes `pipeline_run` today. `DELETE FROM pipeline_run
   WHERE started_at < now() - INTERVAL '90 days'` cascades to the child table —
   which is the reason the FK declares `ON DELETE CASCADE`.

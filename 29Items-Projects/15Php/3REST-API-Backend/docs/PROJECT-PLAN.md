# REST API Backend — Project Plan

> **Marketplace / SaaS backend** built on **PHP 8.3 + Laravel 11**, **MySQL 8**, **Redis 7**, with a **Vue 3** admin/storefront client.
> Features: token auth, versioned & rate-limited REST API, event-driven notifications, and user-behavior clustering for personalization & recommendations.
> Ships to **DigitalOcean** via **GitHub Actions**. API docs auto-generated with **Swagger / OpenAPI** (L5-Swagger). Tested with **PHPUnit**.

## 1.1 Project File Structure

The repository is a **mono-repo** with three top-level application concerns (`backend/`, `frontend/`, `docker/`) plus shared CI, docs, and tooling at the root. This keeps the Laravel API, the Vue SPA, and the container definitions versioned together so a single PR can move a feature across the whole stack.

### Why this layout

| Decision | Rationale |
| --- | --- |
| **Mono-repo** | One source of truth; atomic cross-stack PRs; simpler local orchestration via a single `docker-compose.yml`. |
| **`Api/V1` namespace** | URI-based versioning (`/api/v1/...`) is the most cache- and client-friendly scheme; new versions add a sibling `V2` folder without touching `V1`. |
| **Form Requests + API Resources** | Enforces a clean **input boundary** (validation) and **output boundary** (serialization) so controllers stay thin and contracts stay explicit for Swagger. |
| **Service + Repository layers** | Keeps domain logic and persistence testable in isolation; the clustering/recommendation logic never leaks into controllers. |
| **Events / Listeners / Notifications** | Native event-driven path: an HTTP request emits a domain event; queued listeners do the slow work (notifications, telemetry) off the request thread. |
| **`docker/` + root `docker-compose.yml`** | Infra-as-config lives beside the code it runs; identical images locally and on DigitalOcean. |
